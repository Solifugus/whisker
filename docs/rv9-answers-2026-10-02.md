## 1. `MAX_CONTOURS` — all three options, and a fourth you did not ask for

You offered log, refuse, or raise, with no preference between the first two.
**Logged and raised**, because they answer different questions: the log is for
the person whose picture came out wrong, the cap is for the picture.

Reproduced first, with your own programme, and then *looked at* —
`keys_onepath.ppm` is the argument. It does not look broken. It looks like a
keyboard somebody styled that way, which is exactly why a localised silent
truncation is worse than the `SRC_MAX` wedge it resembles.

**It says so now**, once per document rather than once per band:

```
W rv9-svgwin: path truncated: 8 subpath(s) past 64, 0 point(s) past 256
              -- the rest of the document drew
```

`end_contour` had been dropping an overflowed contour down the same branch as
one *too short to be a contour* — a different thing, and only one of them is
worth telling anybody about. `MAX_PTS` needed catching in a second place:
`parse_path` leaves its loop when points run out, so `emit` is never called
again and counting there missed it entirely.

**The cap is 64**, and the buffer moved off the stack to get there. This is the
part worth your attention, because the obvious version of option 3 would have
cost you: `rcontour_t cs[MAX_CONTOURS]` was a *local* in `do_path`, so raising
it would have raised the stack requirement of every program that writes to
`/w0`. It sits beside `pts` in the device state now, and 64 costs 512 bytes of
the window's own heap, once. At four points a subpath it is `MAX_PTS` that
binds next, at 64 quads exactly.

**Your keyboard result changes.** Re-run `tools/evidence/keyboard/run.sh`
against this tree:

```
  C  one path for all   1879 bytes   25132 key px   fits
  C draws +0 key pixels against A (+0%): the same keyboard
  MAX_CONTOURS is 64, and this keyboard wants 36 outlines
```

So form C is now both correct and the cheapest — 1,879 bytes against B's 1,960
and A's 3,361. The 52 % figure in your design is B against A; C is 56 % of A
*with* ids and the one to reach for.

**The ceilings are askable**, which is the smaller ask and the one that keeps
working when the constants stop being constants:

```c
rv9_svg_limits_t l;
env->getstat(w0, RV9_SVG_GS_LIMITS, &l);   /* src_max, pts_max,
                                              contours_max, depth_max */
```

They are now in `docs/reference.md` §9 as well — they were in **no** RV-9
document at all, which you were right to notice. Keep carrying 16 as a hard
count if you like; a limit you hope to stay under is not a limit, and the
getstat is there for when you would rather not guess.

## 2. Both modules run, and neither stack declaration was right

`wflick`, `wcompose` and `flick` are all on the board and both modules are
committed. The comparison you asked to be run first, same panel, same session:

```
flick     full 57 ms, 194 B    press 19 ms, 146 B    release 19 ms
wflick    full 79 ms, 360 B    press 32 ms, 342 B    release 28 ms
```

Unchanged from 2026-09-30 — the refreshed header costs nothing at render time.
Two thirds of the press difference is still geometry rather than whisker: your
tree gives the button 64 rows where `flick` chose 48 by hand. Per band it is
3.2 ms against 4.1 ms.

`wcompose` draws what it claims: two stacks over one background, and the
clipped repaint of STOP leaves the stack below untouched with the band
carrying the scene rather than the device colour.

### The stack, and why it is the interesting part

```
wflick    5120 overflows, 6144 runs  ->  7168 declared
wcompose  4096 runs                  ->  5120 declared
```

`wflick` had **4096 from my own bisection two days ago** and overflowed after
the refresh; `wcompose` had 2560 copied from it. So both of us have now been
wrong about this, which suggests the number is not where either of us was
looking.

It is not. `-fstack-usage` says `wflick`'s deepest frame is **352 bytes** and
`wcompose`'s is **528** — nowhere near either figure. The rest is not yours:

> **Drawing to `/w0` renders on the writer's stack.** `modules/pic` already
> recorded this ("measured peak 2080 drawing to /w0, which renders on the
> writer's stack"). whisker **streams rather than buffers**, so the `put()`
> that completes a document runs the entire renderer *with every layout frame
> still live beneath it*. The two depths add.

That is a real consequence of `wflick`'s stated choice — *"nothing is buffered.
The sink hands each piece to write() as it is produced, so a 4 KB document
never needs 4 KB of a program's memory"* — and the trade is sharper than that
sentence suggests. You save the 4 KB buffer and pay for it in stack, at the
worst possible moment. It is still probably the right choice on a machine where
heap is the scarce thing; it belongs in `design.md` rather than in a surprise.

A buffering sink would pay the two depths *separately* and could declare a
smaller stack. Worth a measurement rather than a decision.

### `wcompose` had `wflick`'s old window check

Copied before I fixed it. `RV9_GS_SIZE` cannot answer *"is this a window"* —
it is the generic how-big-is-this code and RBF answers it with a file's length.
It probes `RV9_SVG_SS_ROWS` now, and `wcompose > /r0/x` is refused on the board
instead of laying itself out on a 0×0 screen.

### Your two questions

**The store, not `.nostore`.** `.nostore` exists for `downloaded`, whose whole
purpose is to arrive by some other route so `load` can be tested. These are
demonstrations beside `flick` and `pic`. The store is 88,832 bytes — **8.4 %**
of its megabyte, so size was never the question.

**The copy stays, and now says which copy it is.** `modules/whisker.from`
records the upstream commit, date and subject; it is a separate file because
the provenance cannot live inside the header without breaking the one check
that matters, which is byte-identity.

The reasoning is unchanged and I think it survives your objection. An include
path into `~/development/whisker` breaks every clean checkout of a repository
that is on GitHub and cloned by people who do not have whisker at all. And
*"somebody had to refresh it"* is not staleness — it is pinning working. A
module built against an older copy is built against a known version, which is
the point. The thing to avoid is a copy nobody can identify, and that is now
fixed rather than argued about.

Deliberately **not** wired into `run.sh`: a gate that passes or fails depending
on what happens to be on the machine is worse than no gate.

## 3. For when the P4 lands

Noted, and nothing wanted. Touch slop staying open until the controller says
what it needs is the right call — it is the same shape as leaving `wcet_us`
undeclared until a loop has run.

One thing from this round that will matter then: the **stack** finding scales
badly in the direction you are heading. A 1024×600 panel is 75 bands against
22, and the renderer runs on the writer's stack for every one of them. If a
whisker program on the P4 declares a stack from C5 measurements it will be
wrong in the dangerous direction. Measure it there before trusting it.

## Addendum, 2026-10-03 — physical size, and two things found in `wstat`

### `RV9_GS_PHYSICAL` exists

Matthew asked whether a device can be asked how big it is in the world, read
the proposal, and raised the question that shaped it: **what about a driver
where the physical size actually varies?** So the answer carries a `kind`:

```c
rv9_physical_t ph;
env->getstat(w0, RV9_GS_PHYSICAL, &ph);   /* width_um, height_um, kind */
```

| `kind` | |
|---|---|
| `RV9_PHYS_FIXED` | Glass. Measure once, cache forever. |
| `RV9_PHYS_VARIABLE` | A projection. True now; **ask again.** |
| `RV9_PHYS_UNKNOWN` | Understands the question, cannot answer today. |

A device with no opinion at all answers `RV9_IO_ERR_UNSUPPORTED`. Treat that
and `UNKNOWN` the same: work in pixels.

It is a **generic** code (7), not a driver-private one, because any device with
a physical presence could answer it. `/w0` and `/term` both do, off the same
glass. On the board:

```
rv9> screen /term
screen: 32.9 x 17.7 mm        landscape, swapped with the pixels
rv9> screen
24 rows x 80 cols             a terminal on a wire, so no millimetres
```

**The rotation is the trap.** The millimetres turn the same way the pixels do,
so `width_um / width_px` is a pitch. A surface that rotated one and not the
other hands back an inverted aspect — a wrong answer that looks plausible. The
host harness did exactly that, and the check written for it caught the harness
rather than the firmware.

**The C5's figures are derived, not measured** — a 1.47-inch diagonal over
172:320 gives 17.68 × 32.89 mm. `PANEL_W_UM` in `panel.c` is the place to
correct if a caliper disagrees.

**What this unblocks for whisker**, and it is the reason it was worth doing:
"size widgets in pixels, let a bigger screen hold more of them" is right for
the frame budget and wrong for anything meant to be touched, because 64 rows is
6.6 mm here and 9.6 mm on the P4. Those two rules disagree and only one of them
was askable. Now both are.

### `wstat` did not start

`devices="/w0,/tsens"` is **one device name**. The manifest list is
space-separated, and admission said so exactly — *"it needs /w0,/tsens, which
this machine does not have"* — refused at fork, before the program ran.

### `wstat`'s stack was pessimistic, and the reason generalises

It arrived at 8192 with the honest note that it had not been bisected, and an
estimate of *"a minimum somewhere near 6432"* from the call graph plus
`wflick`'s measurement. Bisected on the board: **it runs at 5120.** Declared
6144.

So `wstat` needs *less* than `wflick` despite a deeper chain of its own — and
the reason is worth carrying into `tools/evidence/stack/`:

> **The renderer's stack depth depends on what the DOCUMENT contains, not on
> the program.** `wflick` draws corner marks, so it reaches `do_path` and
> `rv9_raster_fill_n` — a 624-byte frame by itself. `wstat`'s 138-byte readout
> has no paths in it at all.

A figure measured with one document does not transfer to another. The document
to measure with is the richest thing the program can emit, not the one it
happens to draw first.

That is three stack declarations in two days that were reasoned rather than
measured, and all three were wrong — two low, one high. The call graph is a
good way to find the *shape* of the answer and a bad way to find the number.

### Your §7 asked for four things, and I had delivered three

Read `docs/scale-sketch.md` §7 after building it, which was the right order by
luck rather than design. Three matched without coordination — both dimensions
rather than a diagonal, a distinct unknown, `uint32` micrometres.

The fourth did not: **"in the same record as the pixel size"**. You were right
and I have changed it. `rv9_physical_t` is 20 bytes now:

```c
uint32_t width_px, height_px;   /* always real */
uint32_t width_um, height_um;   /* 0 unless kind says otherwise */
uint8_t  kind;
```

`width_um / width_px` is a pitch, and two calls could straddle a rotation —
or, on a `VARIABLE` device, a move. `RV9_GS_SIZE` still answers pixels alone
for anything that only wants those.

Worth doing now precisely because there is no caller yet, which is what your
sketch said and what the limits getstat was in the same position for.

One thing your §7 asked of whisker rather than of RV-9, and I think it is the
important half: *"whisker must work when it is absent, which it will be on
some hosts forever... fall back to a declared nominal and report that it did,
not guess quietly."* `kind` is what makes that tellable. Treat `UNKNOWN` and
`RV9_IO_ERR_UNSUPPORTED` the same.

### A hazard worth knowing before you build against this

I flashed firmware without rebuilding the module store, and `screen` —
compiled against the 12-byte layout — read `width_px` as `width_um` and
reported **0.3 × 0.2 mm** for 320 × 172. Nothing caught it.

A struct layout change in `module.h` is an ABI change that `abi_version` does
not capture, because `mkmodule.py` stamps every module 1 whatever it uses
(`reference.md` §5 records that gap). It is harmless in practice — modules
always flash beside the firmware — but it is quieter than the failure §5
describes, and it is the reason a vendored `whisker.h` plus a stale module
store would be two ways to be out of step rather than one. If you refresh
`modules/whisker.h`, run `tools/build_modules.sh`, not just `idf.py flash`.
