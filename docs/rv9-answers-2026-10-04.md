## The prerequisite, then the line

You were right that it is the refresh or neither, and the reason is the one
that matters: added to the tree as it stood, `#define WSK_MINIMAL 1` would have
compiled cleanly, changed nothing, and left `<path d=` in the binary while the
source claimed otherwise. A false guarantee a reader can see is worse than no
guarantee.

**Refreshed.** `modules/whisker.from` now records **`e7d1a4a`** — the last
commit that actually touched `src/whisker.h`, which is *newer* than the
`60a28e4` your note named. You committed five more times while writing it.

Both lines are in. The figures on this toolchain:

```
wstat    5320 -> 4636 code+rodata     <path d= in rodata: 1 -> 0
wfont    3588 -> 2896                                       1 -> 0
wflick                                                           1

```

The two that mark keep their path; the two that do not, do not.

## I did not re-bisect, and the figure did not move

You asked for that and for a shout if it did. It did not, and I checked both
claims behind it rather than taking them:

| | |
|---|---|
| the module's own entry frame | **640 bytes** with and without the profile |
| the document `wstat` emits | **138 bytes** before and after |

So 6,144 stands, measured once and now structural rather than incidental —
which is the whole argument for the line and it is a good one. A later
`WSK_MARK_CORNERS` is refused by `wsk_check` with `WSK_E_KIND` instead of
quietly reaching `do_path` and a 624-byte frame.

## `wfont` got it too, which you did not ask for

It is labels only, and its `build.conf` derives its stack from `wstat`'s. So
leaving marks reachable there would have left a *derivation* one edit from
being wrong — the same hazard one step further along, and the inconsistency
would have been odd to read. If that is not wanted, it is one line to revert.

## One risk your note did not raise

`wflick` and `wcompose` had their stacks bisected against the **old** header.
Both still run, and `wflick`'s numbers are unchanged to the millisecond:

```
wflick: full 77 ms, 360 bytes, press 32 ms, 342 bytes, release 28 ms, 235 bytes
wflick: clipped rows 32..96 of 172
```

Worth building into the ritual: a header refresh is a rebuild of every module
that includes it, and their stack figures were measured against the old one.
Here nothing moved; next time it might.

## `wfont` drew, and only you can read it

```
rv9> wfont > /w0
wfont: 433 bytes. Read it from where you would really read it; the smallest
       row you can read is the floor.
```

Its header is the best argument in it — the renderer's own signal says where
*it* struggles rather than where a person stops reading, and a development
monitor at 4.0 px/mm cannot stand in for a panel at 9.7, so a font-10 cell is
4.1 pixels there and the floor would come out two sizes too high. That is
exactly the case where I can draw it and not see it, same as the corner marks
on 2026-09-30. The answer is Matthew's to give.
