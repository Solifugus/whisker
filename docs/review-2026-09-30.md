# Review — the substrate, run rather than read

**Written 2026-09-30**, against the four documents as they stood at commit
`efc4717`. Nothing was implemented; this is a review of the design and of the
ground it stands on.

**Method, and why it differs from the last one.** `docs/rv9-review.md` was
written by reading RV-9 and was right about thirteen claims of sixteen. This
one was written by *running* it: the driver was built through
`tools/hosttest`'s stubs and driven with documents chosen to answer a question,
and the module rules were tested with the real `riscv32-esp-elf` toolchain,
`modules/module.ld` and the double-link check from `tools/build_modules.sh`.
Every number below came out of a program on this machine on 2026-09-29/30.
The programs are kept in `tools/evidence/` and each prints the claim it
supports.

Where this says **measured**, a program produced it here. Where it says
**argued**, it is reasoning. §6 lists what could not be checked at all.

---

## 1. Verdict

The thesis holds, the two functions are the right two, and the six decisions
survive the check. Three of the findings below are live defects in RV-9 rather
than in this design; one invalidates the most natural shape for whisker's
public API; one is a fact about the font that iteration 1 cannot be written
without and that no document records.

None of them argues against the project. Four of the five argue for settling
something *before* the first line rather than after.

**One mechanism neither document records: the clip is one-shot.** `render()`
sets `clip_y0 = clip_y1 = 0` after every document (`drv_svgwin.c:1172`), so the
host protocol is setstat-then-write, every time, and a caller that sets the
range once and writes twice gets a full redraw the second time.

## 3. Five findings

### 3.1 A `static const` widget tree is not position independent today — and the fix costs nothing

`docs/design.md` §4.1 and `rv9-answers.md` §2.5 both say *no `static const`
array of pointers*. **Measured, the rule is stricter than that and its stated
cause is wrong.** With RV-9's current flags, *any named `static const` object*
referenced from module code fails the double-link check. A string blob with
integer offsets fails. A struct array with inline `char[N]` fields fails.
Neither contains a pointer.

The cause is the link base, not the construct. At `. = 0` the linker relaxes
the `auipc`/`addi` pair into a single `li s0,96` — an absolute address —
because the address fits in an immediate:

```
linked at 0:            linked at 0x4000:
  li   s0,96              auipc s0,0x0
  li   s3,108             addi  s0,s0,92    # 406c <TREE>
```

`modules/dump/dump.c:19` gave up a hex lookup table over this and recorded the
symptom — *"a `static const` array inside a function is a variable at a fixed
address"* — rather than the cause.

**Measured, three ways of building each shape** (`tools/evidence/module_shapes`):

| shape | today | `-Wl,--no-relax` | both links at a non-zero base |
|---|---|---|---|
| struct array holding `const char *label` | fail | fail | **fail** (genuine) |
| one string blob + integer offsets | fail | pass | **pass** |
| inline `char[N]` fields in the struct | fail | pass | **pass** |
| function-pointer table, runtime index | fail | fail | **fail** (genuine) |
| the same dispatch as a `switch` | pass | pass | pass |
| tree built on the stack at runtime | pass | pass | pass |
| `switch` over an `int` returning literals | pass | pass | pass |

Linking both the shipped module and the probe at a non-zero base — `. = 0x4000`
against `. = 0x8000` — costs **nothing**: all 84 modules still pass and the
total comes to **71,732 bytes either way, byte for byte**. `-Wl,--no-relax`
also works and costs **+9.5%** (71,732 → 78,572). The check keeps catching both
genuine failures under either fix.

**Why this reaches whisker and nothing else.** No RV-9 module declares static
const *data* at all — every one of them is a function returning literals — so
nothing has met this. whisker is the first thing that is declarative data, and
a caller's panel written as

```c
static const wsk_widget_t panel[] = { ... };
```

is the shape the library exists to make possible. Today it does not link. The
decision to take before iteration 1 is whether whisker requires the tree to be
built at runtime — which works everywhere, and is what `tools/evidence` shows
passing — or whether RV-9 changes the link base first and the declarative form
becomes legal.

Note also the rule that is **not** relaxed by any of this: a table of function
pointers, indexed at runtime, fails under every variant. §4.1's warning about
the widget dispatch table is right, and the `switch` form beside it passes.

*Confirmed in passing:* `uint64_t % 3` failed to link with `undefined reference
to __umoddi3`, exactly as `modlib.h` says it does.

### 3.2 Exceeding `SRC_MAX` does not truncate the picture — it kills the window

**Measured** (`tools/evidence/svgwin_facts`, section 1). A 5,025-byte document,
then two valid ones, on one open path:

```
oversized document (5025 bytes):       0 blits
a valid document written afterwards:   0 blits   -> the window is WEDGED
and again:                             0 blits
```

Past `SRC_MAX` the bytes are dropped (`drv_svgwin.c:1262-1268`), so the
`</svg>` terminator never lands in the buffer, `s->len` stays pinned at 4,096,
and the six-byte comparison that ends a document can never match again. Every
later document on that path is dropped too. No warning is logged either: the
*"document over 4096 bytes; drew what fitted"* line lives inside the branch
that never runs.

**The consequence for this design.** `docs/design.md` §2.3 says to respect the
ceiling *for the right reason — time, paid once per band*. That is true and it
is not the whole reason. The ceiling is a cliff, and the failure is silent and
permanent. So:

- `render` needs a **byte budget and a defined refusal**, not an assertion in a
  test that a dozen controls happen to fit. A caller that adds a widget at
  runtime must be told no, in a way it can act on, rather than losing the
  window.
- §5's done-criterion 1 should assert the refusal as well as the fit — the
  control case, in the terms of this project's own evidence standards.

The defect is RV-9's and the fix is small; it is filed in RV-9's roadmap. But
whisker must be correct against the device as it is, because a whisker that
only behaves on a fixed RV-9 is a whisker that wedges the board in the field.

### 3.3 A `<` in label text hangs the window device, and escaping is not available

**Measured.** `<text>a &lt; b</text>` with a *raw* `<` never returns: >20 s
where a full frame is 0.3 ms. The backtrace lands in `attr()`. The root cause
is at `drv_svgwin.c:129-133` — the attribute-name scan stops on `/` or `>`,
and then

```c
if (p >= tend || *p != '=') continue;
```

restarts the loop **without advancing `p`**. A raw `<` in content makes the
parser read the rest of the text as a tag, and since every text element ends
`</text>`, the scan always reaches a `/`. The loop is inside `svgwin_write`,
holding `s->lock`, on one core.

**And the obvious defence does not exist: entities are rendered literally.**
Measured: `a &amp;lt; b` draws the four characters `&amp;lt;` on the panel — 54 inked
columns against 25 for the raw form.

So whisker can neither escape text nor pass it through. **Label text has to be
validated at the API boundary**: ASCII 32..126, minus `<`, `&` and `>`. Two
consequences worth writing into §5:

- Done-criterion 1 as written — *"output parses"* — and a correct picture are
  different documents once a `&` is in a label. An escaped `&amp;amp;` parses and
  draws wrongly; a raw `&` draws right and does not parse. The only consistent
  answer is that such a label never reaches the emitter.
- Non-ASCII is the quiet version of the same. Measured: a UTF-8 degree sign
  consumes **two cells and draws nothing**, because `do_text` advances per
  *byte* and `rv9_glyph_cov` blanks anything outside 32..126. Byte counting
  keeps whisker's width arithmetic in agreement with the driver, so the layout
  stays right — the glyphs are simply absent.

### 3.4 The backing rect must cover the snapped rows, not the widget's rows

This is `flick`'s bug once more, in the form the rule as currently written does
not prevent. The rule on `RV9_SVG_SS_ROWS` says *a clipped document must carry
every pixel of its rows*, and "its rows" reads as the widget's.

**Measured.** Clip 100..140 — deliberately not band-aligned — with a backing
rect covering exactly 100..140, over a navy scene on a black device
background:

```
row  97  (band 96..104, above the backing)   #000000   <- black strip
row 102  (inside the backing)                #102039
row 142  (band 136..144, below the backing)  #000000   <- black strip

with the backing snapped out to rows 96..144: #102039 at both
```

Because the clip snaps outward and each band is cleared in full before
anything is drawn into it, the rows that must be carried are the **band-aligned
ones**.

**For iteration 1:**

- `rows(tree, ids, n)` should return the **snapped** range, and
  `render(tree, ids, n)` should size the backing from that same range, so the
  two cannot disagree.
- Done-criterion 3 must assert it **at a widget that is not 8-aligned**. An
  aligned widget passes without exercising the rule — which is precisely the
  control-case failure `CLAUDE.md` describes, in a test that would otherwise
  look thorough.
- Done-criterion 4 (heights on multiples of 8) is a performance rule, and this
  is a correctness rule. Keeping them separate matters, because the moment a
  caller sets an explicit height the alignment goes and the backing must still
  be right.

### 3.5 Text metrics are exactly computable, and no document says so

The renderer cannot lay out a label without knowing how wide it is, and nothing
in the four documents says where that number comes from. It is already
determined:

- one fixed-width face, glyph cell `RV9_GLYPH_W` 10 by `RV9_GLYPH_H` 20
- **advance per character = `font_size * 10 / 20`**, i.e. half the font size
- **cell top = `y - font_size * 15 / 20`**, cell height = `font_size`
  (`RV9_FONT_BASELINE` 15, and SVG puts `y` on the baseline)
- glyphs exist for 32..126; anything else is blank but still advances

**Measured:** five `M`s at `font-size="20"` from `x="20"` produced ink from
column 20 to 68 — 49 columns inside the predicted 50-column advance, the
missing column being the gap the glyph leaves in its cell. Predicted cell rows
25..45, measured ink 28..39, which is the cap height sitting inside the cell.

**And `text-anchor` is honoured**, computed on that same advance box:
`"CONFIRM"` anchored `middle` at `x="160"` produced ink centred on column 159.

So whisker can size, centre and truncate labels with 32-bit integer arithmetic
and no font API — and centring a button label costs **one attribute** rather
than a computed `x`, which is also the cheaper thing to emit. This belongs in
§2.1 beside the rest of what the substrate already provides.

## 4. The byte budget, measured

A realistic control panel — a full-width backing, then a rounded `rect` and a
centred `text` per control — emitted three ways
(`tools/evidence/svgwin_facts/bytes.c`):

| controls | attributes on every element | shared ones on a `<g>` | `<g>`, and no `id` |
|---|---|---|---|
| 12 | 1,960 B | 1,439 B | 1,341 B |
| 20 | 3,217 B | 2,312 B | 2,142 B |
| **fitting under `SRC_MAX`** | **25** | **36** | **39** |

Marginal cost per control: **157 B → 109 B → 100 B**.

Three things follow.

1. **`rv9-answers.md` §3.4 is right in kind and now has a number.** 4 KB binds
   at about 25 controls, not 20, and the honest ceiling on a 1024×600 panel is
   25 to 39 depending on how the document is written.
2. **Hoisting the shared presentation attributes onto a `<g>` buys 44% more
   interface**, and it is paid again on every band of every repaint, at
   0.00036 ms per byte per frame. That is an emission rule, not a style
   preference, and it should be in §5.
3. **`id` attributes cost about 8% of the budget and RV-9 ignores them.** D4
   stays right — the id is the address space, and `hit` reads it from the tree,
   not from the document — but *emitting* ids buys nothing on RV-9 while
   costing bytes per band. They earn their place on a host with a real DOM
   (gBASIC, Linux) and in debugging. Suggest a flag: ids in the full document,
   no ids in a clipped repaint.

Both documents were rendered to a PPM and looked at, per the house rule. The
320×172 panel reads correctly. The 1024×600 one shows something no measurement
reports: **a big screen wants a grid, not a longer column.** Thirteen
full-width bars is a list rather than an interface. That is the visual case for
the 2×2 grid §4.3 already prices as affordable, and it is the one place where
*"let a bigger screen hold more widgets rather than bigger ones"* needs a
companion rule — widget heights can stay fixed, but text has to stay legible.

## 5. Points on the documents themselves

- **38 ms is work per tap, not acknowledgement latency.** `flick` times three
  draws; press is 19 ms and release is 19 ms, and the finger lifts between
  them. What a person waits for after touching is the press. The design uses
  38 ms as a latency budget *and* as a cost, and iteration 2's end-to-end
  measurement will need the two kept apart.
- **The output buffer contract is unspecified.** `render(tree) -> SVG text`
  implies a 4 KB buffer in a program budget of roughly 39 KB, with no allocator
  in `rv9_mod_env_t` and modules typically declaring 1.5–3 KB of stack
  (`PROC_DEFAULT_STACK` is 8,192; `build.conf` files ask for less). A sink form
  — `render(tree, sink, ctx)` — keeps the buffer form for tests, lets §3.2's
  byte budget be enforced *during* emission, and costs nothing in position
  independence, because a function pointer **passed** is fine and only a stored
  table is not.
- **The touch target has a number.** The P4 is about 170 dpi (1,187 px diagonal
  over 7 inches), so a 9 mm finger is about 60 px: **64 rows — eight bands, and
  band-aligned** — is the natural minimum button height, which lands exactly on
  §5's item 4.
- **§6's third bar may rule whisker out for the wrong reason.** A Linux host
  still needs a window and an event loop from somewhere; `raster.c` gives the
  pixels, not the surface. The bar that measures the right thing is whether
  whisker shrinks gBASIC's GTK contact from 21 widget types and 70 `gi` call
  sites to a window, a blit and a click — which is a real win, and can be
  estimated before anything is built.
- **gBASIC's `docs/gui_addressability_design.md` §0.3 still quotes "30 ms
  against 59 ms"** and cites whisker's design for it. `CLAUDE.md` says not to
  quote those from any document that still carries them; that document is one.
- **Ask for the `SRC_MAX` getstat now.** RV-9 offered it and there is no caller
  yet. §3.2 makes guessing it expensive, and it differs between the boards.

## 6. What could not be verified

- **Nothing was run on hardware.** Every measurement here is the host build
  through `tools/hosttest`'s stubs. The timings quoted from RV-9 remain RV-9's.
- **§3.1's shipped-module failure is inferred at one step.** What was measured
  is that the two links differ and that the base-0 link contains `li s0,96`, an
  absolute address. That a module holding it misbehaves when the loader places
  it elsewhere follows from the loader's contract; it was not run on the board.
- **The C5 panel's physical diagonal is not recorded in RV-9**, so its dpi —
  and therefore whether a fixed pixel height is the same physical size on both
  boards — could not be checked. Only the P4's dpi is computed above.
- **No end-to-end tap has been measured by anybody**, which `docs/design.md`
  §3 already says and this review cannot change.

## 7. What to change, concretely

1. **§2.1** — add the font metrics (§3.5). The renderer cannot be written
   without them.
2. **§2.2** — add that the clip is one-shot, and that the backing must cover
   the **snapped** band range, not the widget's rows (§3.4).
3. **§2.3** — record that exceeding `SRC_MAX` wedges the window rather than
   truncating the picture (§3.2), and that `render` therefore needs a byte
   budget and a refusal.
4. **§2.4** — add: no entities, and text restricted to ASCII 32..126 minus
   `<`, `&`, `>`, because a `<` hangs the device and an entity draws literally
   (§3.3).
5. **§4.1 / D1** — correct the module rule. It is not *"no static const array
   of pointers"*; it is *"no named static const object"* under today's link
   base, and there is a zero-cost fix RV-9 can apply (§3.1). Decide whether
   iteration 1 requires a runtime-built tree or waits for that fix.
6. **§5** — the surface becomes:
   `render(tree, sink, ctx)`, `render_clipped(tree, ids, n, sink, ctx)`,
   `rows(tree, ids, n, device_h)` returning the **snapped** range.
   Add the `<g>` hoisting rule and the optional-id flag (§4).
7. **§5 done-criteria** — criterion 1 gains the refusal case; criterion 3 gains
   a **non**-8-aligned widget; add a criterion that a label containing `<`, `&`
   or a non-ASCII byte is refused by `render` rather than emitted.
8. **§5** — default button height **64 rows**, from the P4's dpi, not from the
   C5's proportions.
9. **§2.2 / §3** — separate the 19 ms acknowledgement from the 38 ms pair,
   and say which one iteration 2 is measuring against.
10. **§6** — restate the Linux bar as a reduction in GTK surface rather than
    its elimination.

Filed against RV-9, with reproductions, in its `docs/roadmap.md`: the
`SRC_MAX` wedge, the `attr()` hang, and the link base. None of the three is
whisker's to fix, and all three shape what iteration 1 must be correct against.
