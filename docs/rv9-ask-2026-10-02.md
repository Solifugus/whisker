## 1. `MAX_CONTOURS` is 16, it is undocumented, and it fails silently

**This is the one worth your time.**

`drv_svgwin.c` caps a `<path>` at `MAX_CONTOURS` (16) and `MAX_PTS` (256).
Past 16 subpaths, `parse_path` stops and `do_path` fills what it got. The rest
of the document draws normally around the hole.

Measured, not read — `tools/evidence/keyboard/` in whisker:

```
./run.sh              # 1024x600
./run.sh 320 172      # the C5
```

It draws the same 36-key keyboard three ways. The third puts all 36 key
outlines in one `<path>`:

```
  C  one path for all   1967 bytes   83152 key pixels   (A draws 209826)
  C draws -126674 key pixels against A (-60%)
```

**Twenty of the thirty-six keys are not drawn. All thirty-six labels are.** Look
at `keys_onepath.ppm` — it is a keyboard with twenty invisible keys and nothing
to say so. `MAX_PTS` is not what bit: 36 rectangles is 180 points, well under
256.

And the log says it succeeded:

```
I rv9-svgwin: drew 1967 bytes in 3 ms
```

**The ask is your own principle, applied to a case you have not hit yet.** When
you fixed the `SRC_MAX` wedge on 2026-09-30 you wrote that you drop the document
and log it *"because half a picture is a silent wrong answer where an unchanged
screen plus a log line is a legible one."* A path truncated at 16 contours is
exactly half a picture, and it is worse than the `SRC_MAX` case in one way: the
failure is **localised**, so it reads as a bug in whichever widget happens to be
missing rather than as a problem with the document.

Three options, and the choice is yours — we have no preference between the first
two:

1. **Log it.** `W rv9-svgwin: path truncated at 16 contours` costs almost
   nothing and turns a silent wrong answer into a legible one.
2. **Refuse the path**, the way an oversized document is refused.
3. **Raise the cap.** `rcontour_t cs[MAX_CONTOURS]` is on the stack in
   `do_path`, so 64 would cost 64 × `sizeof(rcontour_t)` of stack in one
   function — your call entirely, and we would rather have the log either way.

**A second, smaller ask in the same breath.** You offered a getstat for
`SRC_MAX`. If that happens, `MAX_CONTOURS` and `MAX_PTS` are worth the same
treatment: they are the other two ceilings a generator has to respect, neither
is in `docs/reference.md`, and a caller that has to discover them by drawing a
wrong picture will. whisker will carry 16 as a hard count in its own code
regardless — recorded in `design.md` §2.3 — because a limit you hope to stay
under is not a limit.

## 2. Two things are staged, uncommitted, in your tree

Both for you to validate, change or drop. Neither has ever run on hardware.

### `modules/whisker.h` — **modified**

A byte-identical copy of whisker's `src/whisker.h`. The copy you committed was
from iteration 1; this one carries `hit`, composition and the text field. It is
refreshed because `wflick` includes it and would otherwise be built against a
header two iterations old.

**The open question is still the one from last time:** keep a vendored copy, or
add an include directory to `build.conf` and point at
`~/development/whisker/src`? A copy cannot go stale silently if somebody
remembers to refresh it, and this is the second time somebody had to. Your
tree, your call.

### `modules/wcompose/` — **new**

```
wcompose > /w0
```

A toolbar across the top and two buttons under it: **two independent widget
stacks, one document, one background**. Then STOP is marked pressed and only its
rows are rewritten through `RV9_SVG_SS_ROWS`, with both stacks still offered to
the document.

Three things to look at, in order of what they would cost to find later:

1. both stacks on the panel at once, with **one** scene behind them;
2. the pressed repaint leaving the stack below untouched, and the band coming
   back carrying the scene rather than the device background — the thing
   `flick` got wrong for months;
3. **the corner marks on the pressed button, on the real glass.** They are a
   quarter of the button's height capped at 16 px, and they have been drawn at
   matched physical size on a desktop monitor but never on 1.9 inches.

Both modules build clean under `tools/build_modules.sh` — `wflick` 4,612 bytes,
`wcompose` 4,448 — and all 84 other modules still build beside them.

**Two questions we cannot answer from here:** whether either belongs in the
flash store or in `.nostore`, and whether `stack_size=2560` is right for
`wcompose`. It holds two trees, a document and two widget arrays on the stack;
2560 was copied from `wflick` rather than bisected.

**And one thing to run first, if you run anything:** `flick` and then `wflick`,
back to back, on the same panel. `wflick` is `flick` generated from a widget
tree instead of written as three string literals, and the whole question is what
that costs — in bytes, in milliseconds, and in whether the picture is still
right.

## 3. For when the P4 lands

The measurement nobody has taken is **finger-down to pixel-changed, end to
end**. That number includes an I²C controller, an interrupt, a process wakeup
and a repaint, and the 19 ms in `rv9-answers.md` §7 is only the last of those.

It needs a touch driver, which does not exist. Whenever that happens, whisker
has one open question that only real hardware can close: **touch slop** —
whether a tap two pixels into a gap should count. It is deliberately unanswered
(`design.md` §5b) because the right tolerance depends on how accurate the
controller's centroid actually is. Exact rectangles today, a number after the
panel says what it needs.

Nothing is wanted before then. The whisker side is written and waiting.

## 4. News, not an ask: `input` is not coming to the C5

Matthew ratified it on 2026-10-02 (`docs/decisions.md` D6): a text field goes
only to hosts that have an input device.

Worth telling you because the reason changed. We assumed the argument would be
bytes — a 36-key keyboard was measured at 94 % of `SRC_MAX`. After composition
and the path form it is **half the budget**, so bytes stopped being the
objection. What remains is that the C5 has nothing to press a key with, and that
a key on a 320×172 panel is about **4 × 4.8 mm** against the **9 mm** a finger
was measured to want (`tools/evidence/finger_size/`).

So on the C5, text entry stays exactly where RV-9 already puts it: over the
terminal, from a machine that has a keyboard. A whisker panel there displays and
commands. That is your design document's position and we are not asking you to
move off it.

## What whisker looks like today, for context

Four iterations, all built, none of them on hardware:

| | |
|---|---|
| §5 | the renderer — labels and buttons in one single-axis stack |
| §5b | `hit` — a point becomes an id |
| §5c | composition — several stacks in one document, one background |
| §5d | `input` — a text field, left-aligned, tail-scrolled, caret on request |

`src/run.sh --module` runs 135 checks: the suite, the documents through a real
XML parser, the pixels through **your** `raster.c` and `font.c`, three modules
double-linked at two bases, and pictures a person looks at.
`host/linux/run.sh --test` adds 19 more, including a click becoming a character
in a field and repainting four bands and nothing else.

Everything whisker claims about RV-9 is in `tools/evidence/`, and every
programme there reports what it finds rather than what it found — so running one
against your tree tells you which RV-9 is in front of you.
