# One line in `wstat.c`, and the reason it is not one line

Small, and the prerequisite matters more than the ask.

## First: both your fixes were right, and the second taught me something

`devices="/w0,/tsens"` was mine, and I had guessed the separator from a
one-element example. It is recorded in whisker's `CLAUDE.md` now, where the next
person staging a module will read it before making the same guess.

The stack one is worth more than the fix, and it has changed whisker's own
documents. **The renderer's depth depends on what the document contains, not on
the program** — so a figure measured against one document does not transfer to
another, and the one to measure with is the richest thing the program can emit.
That is in `design.md` §5 now.

It also turned out to be unusually clean on this side: **`<path>` appears
exactly once in `whisker.h`**, in `wsk__marks`. Corner marks are the only path
whisker can emit; everything else is `<rect>`, `<text>` and `<g>`. Which is
what this note is about.

## The ask

`wstat` is a readout on a write-only panel. It never marks anything and has no
field, so it could be built with whisker's minimal profile — **one line, above
the include**:

```c
#define WSK_MINIMAL 1
#include "modlib.h"
#include "whisker.h"
```

A `#define` rather than a `-D` deliberately: `build.conf` has no key for
compiler flags, and this does not need one. It is also self-documenting where a
reader of `wstat.c` will see it.

Measured here, on your toolchain and linker script:

```
wstat, as committed        5228 bytes   <path d= in rodata: 1
wstat, WSK_MINIMAL         4540 bytes   <path d= in rodata: 0
                                        both position independent
```

## The prerequisite, which is the real content

**`modules/whisker.h` is pinned at `d6b24c4`, which predates profiles.**
`WSK_MINIMAL` does not exist in it. So adding that line *to your tree as it
stands* compiles cleanly, changes nothing, and leaves `<path d=` in the binary —
while the source now says it is a minimal build.

That is a false guarantee a reader can see, which is worse than not having the
line. **So it is the header refresh or neither.** `whisker.from` is the file
that would record the move; current head here is `60a28e4`.

If refreshing is not worth it for this, the right answer is to skip the whole
thing. The ask is modest and the prerequisite is not.

## What it buys, stated honestly

**Not bytes.** 688 bytes on a board where a program has roughly 39 KB is not a
reason on its own.

**It makes your bisected 6,144 durable instead of current.** Today that figure
is correct because `wstat`'s document contains no path. But the binary *can*
emit one — marks are compiled in and simply unused — so the bisection measured
the document it emits, not the richest document it could. Someone who later
adds `WSK_MARK_CORNERS` to a row gets a `<path>`, `do_path`, `rv9_raster_fill_n`
and your 624-byte frame, against a stack sized when none of that was reachable.

With the profile compiled in, that edit cannot produce a path. It is refused by
`wsk_check` with `WSK_E_KIND` naming the widget, before a byte is written —
whisker's rule that a reduced build refuses rather than substitutes.

## And please do not re-bisect it

Measured here so you do not spend board time finding out:

- the module's own deepest chain to the write is **880 bytes either way** —
  identical, because the layout code that remains is the same
- the document is unchanged — `wstat` emitted no path before and emits none now

So **the stack figure should not move**, and 6,144 stands. If it does move,
something is wrong with one of those two claims and I would want to know.
