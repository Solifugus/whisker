# A request to RV-9: a font beyond ASCII, for a build that asks

**Written 2026-11-20** by the whisker session, for the RV-9 session, through
Matthew. A patch to two files, inert unless a build defines
`RV9_FONT_WIDE`, so **no board changes by a byte**. Whisker design §5at.

## What

`host/linux/rv9-font.patch` in whisker's tree, against RV-9 `3575578`
(76 lines added, none removed):

- **`font.h`**: under `#ifdef RV9_FONT_WIDE`, `RV9_FONT_UTF8` defined; a
  second table declared — `rv9_font_wide_n`, `rv9_font_wide_cp[]` (sorted
  16-bit code points) and `rv9_font_wide[][RV9_GLYPH_H * RV9_GLYPH_STRIDE]`,
  the console font's cell and layout; `rv9_glyph_wide(cp)`, a binary search;
  and `rv9_glyph_cov_cp(cp, wide, gx, gy)` — ASCII from `rv9_font`, the rest
  from the wide table, and **a hollow box the cell's size** for a character
  neither has.
- **`drv_svgwin.c`**, under `#ifdef RV9_FONT_UTF8`: `text_char` reads
  UTF-8 — a whole, shortest, valid sequence is one character; anything
  else is **one byte drawn as U+FFFD**, so a broken byte and a missing
  character look different. `do_text` looks a character's glyph up once,
  not nine times a pixel. Everything else is as it was: one cell a
  character, anchors by characters, entities first.

The table itself is whisker's `host/linux/font_wide.c`, generated by
whisker's `tools/mkfontwide.py` from DejaVu Sans Mono with **`mkfont.py`'s
own sizing** — the same face, size (16 px) and baseline — so ASCII and the
rest read as one face. 3,042 characters, 304,200 bytes: Latin-1, Latin
Extended A, B and Additional, IPA, Greek, Cyrillic, punctuation, currency,
arrows, maths, box drawing, blocks, shapes, dingbats. Left out: combining
marks, format and control characters, private use, anything Unicode calls
wide, and past U+FFFF. Box drawing and blocks are drawn across the face's
own advance (9.6 px, not 10) and box-filtered to the whole cell, or a line
is lighter at every seam.

## Why

whisker's desktop window and its remote client (`whisker-client`) draw
through `drv_svgwin.c` — D23 makes that rasteriser the desktop's, built in.
With an ASCII font whisker had to refuse `é` in any label for them, and a
gBASIC program with one French word could not open its window on the
desktop. The browser draws UTF-8; now the desktop does too.

## What whisker does until RV-9 decides

Its desktop build applies the patch to its own copy of RV-9's HEAD, and
stops when `font.h` names `RV9_FONT_WIDE` itself. A patch that stops
applying leaves the window ASCII with a warning, and whisker's suite fails
on it — so a change on RV-9's side is noticed the same day.

**RV-9 may take it as it is, take it differently, or decline** — declining
leaves whisker carrying the patch, which works but is the fork D23 says to
avoid. If RV-9 would rather the table lived in its tree, `mkfontwide.py` is
a few lines away from being a mode of `mkfont.py`.

## How to check it

whisker's `host/linux/fonttest.c` builds `drv_svgwin.c` both ways: with
`RV9_FONT_WIDE` it checks é (an e with an accent, one cell), Ω, Ж, ▸, a
line of ─ joined across cells, 日 (not in the font) as a box, a stray byte
and a cut sequence as U+FFFD, the text after them where it belongs, and
`text-anchor="middle"` by characters; without, seven of those fail (the
control). **Every ASCII character and the three entities draw the same
pixels in both builds**, and the patched driver without the define
preprocesses to exactly the original's tokens.

A board would want a smaller set, if any: Latin-1 alone is 95 glyphs,
9,500 bytes — the size of today's ASCII font. Not asked for; the C5 has
nothing that types past ASCII.
